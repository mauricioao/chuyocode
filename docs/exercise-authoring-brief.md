# How to author exercises for ChuyoCode — brief for an AI model

You are writing English-teaching exercises for a website, and delivering them as
SQL `INSERT` statements for a Postgres (Supabase) table.

**This document is self-contained.** You do not need access to the codebase.
Everything you need — the schema, the closed vocabularies, the payload contract
and the exact output format — is below.

Read all of it before writing a single exercise. The rules in **§6 (Rules that
silently break things)** are the ones that produce broken exercises which no
automated check catches: a learner types a correct answer and is told they are
wrong, with nothing logged anywhere.

---

## 1. The product, in one paragraph

Spanish-speaking developers practising English. They land on a page, pick a
**CEFR level**, then a **language point** (Present simple, Conditionals…), then
an exercise. They answer it in the browser and get instant right/wrong feedback.
There are **no accounts and no saved progress** — every exercise is a
self-contained, stateless attempt.

**All exercise content is in English.** Prompts, options, sentences: English.
The surrounding site interface is Spanish, but you never write that — you only
write exercise content.

---

## 2. The table

```sql
create table exercises (
  id          uuid primary key default gen_random_uuid(),
  slug        text not null,        -- URL segment, English, short, kebab-case
  skill       text not null,        -- writing | listening | reading
  level       text not null,        -- A1 | A2 | B1 | B2 | C1 | C2
  focus       text not null,        -- the language point  (PRIMARY axis)
  topic       text,                 -- the context         (SECONDARY, NULLABLE)
  payload     jsonb not null,       -- the exercise itself
  published   boolean not null default false,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  updated_by  uuid,

  unique (level, focus, slug)
);
```

You produce rows for: `slug, skill, level, focus, topic, payload, published`.
The rest is generated by the database.

### focus vs topic — do not confuse these

| | Question it answers | Example |
|---|---|---|
| **`focus`** | *What am I practising?* | `past-simple` |
| **`topic`** | *Where does it happen?* | `travel` |

`focus` is the primary axis and is **required**. `topic` is context and is
**optional** — set it to `NULL` for a pure grammar drill. Do **not** invent a
context just to fill the column; that pollutes the axis and makes it useless.

---

## 3. The closed vocabularies — copy these slugs exactly

A value outside these lists produces a row that the site cannot route to. It
will not error; the exercise simply becomes unreachable.

### `level`
```
A1  A2  B1  B2  C1  C2
```

### `skill`
```
writing   reading   listening
```
⚠️ **Do NOT use `listening`.** A listening row requires a real, reachable audio
URL, and a fake one renders a broken player. Use `writing` or `reading` only.
There is no `speaking` — nothing can auto-grade speech.

### `focus` — 33 values
```
present-simple          verb-to-be              articles
plurals                 possessives             prepositions
question-forms          present-continuous      past-simple
comparatives            quantifiers             future-forms
adverbs-of-frequency    modal-verbs             present-perfect
past-continuous         first-conditional       second-conditional
passive-voice           reported-speech         gerunds-infinitives
relative-clauses        phrasal-verbs           past-perfect
third-conditional       present-perfect-continuous
modals-of-deduction     linking-words           inversion
cleft-sentences         unreal-past             collocations
idioms
```

The list is roughly ordered by difficulty, but **a focus is not tied to a
level**. `present-simple` is an A1 introduction and again a B1 contrast against
the present continuous. The level lives on each row. Use judgement: do not file
a basic `The cat sits on the mat` drill at B2.

### `topic` — 8 values, or `NULL`
```
daily-life   travel   food   family-and-friends
code-review  daily-standup  technical-documentation  job-interview
```

## 4. The payload — three concepts

Every exercise, of every kind, is the same shape:

```jsonc
{
  "pools": {                        // named sets of selectable items
    "verbs": [
      { "id": "v_sit",  "text": "sit"  },
      { "id": "v_sits", "text": "sits" }
    ]
  },
  "slots": [                        // the things to answer
    {
      "id": "s1",
      "label": "The cat ___ on the mat.",
      "input": "choice",            // the mechanic
      "pool": "verbs",              // which pool to draw from
      "answer": ["v_sits"]          // the correct ITEM ID
    }
  ]
}
```

- **`pools`** — reusable sets of options. One pool can serve many slots; declare
  the options once, not once per question.
- **`slots`** — each is one thing the learner answers. A slot carries its own
  `answer` inline.
- **`label`** — the sentence. Mark the gap with `___` (three or more
  underscores); the input control is rendered **inside** the sentence at that
  point.

An exercise may have **several slots**, and they may use **different mechanics**.
Each slot is graded independently.

---

## 5. The three mechanics

### `choice` — multiple choice (radio buttons)
Needs a `pool` with **at least 2 items**. `answer` holds the id of the correct
one.

```jsonc
{
  "pools": { "opts": [
    { "id": "o_do",   "text": "do"   },
    { "id": "o_does", "text": "does" },
    { "id": "o_did",  "text": "did"  }
  ]},
  "slots": [{
    "id": "s1",
    "label": "___ she work on weekends?",
    "input": "choice",
    "pool": "opts",
    "answer": ["o_does"]
  }]
}
```

### `select` — dropdown
Same shape as `choice`; renders as a `<select>` instead of radio buttons. Use it
when the sentence reads better with an inline dropdown, or when there are many
options.

```jsonc
{
  "pools": { "quant": [
    { "id": "q_a",    "text": "a"    },
    { "id": "q_an",   "text": "an"   },
    { "id": "q_some", "text": "some" }
  ]},
  "slots": [{
    "id": "s1",
    "label": "I would like ___ water, please.",
    "input": "select",
    "pool": "quant",
    "answer": ["q_some"]
  }]
}
```

### `text` — fill in the blank (the learner types)
**No pool.** `answer` holds the accepted strings themselves.

```jsonc
{
  "pools": {},
  "slots": [{
    "id": "s1",
    "label": "She ___ breakfast at eight every morning.",
    "input": "text",
    "answer": ["has", "eats"]
  }]
}
```

Grading trims whitespace and ignores capitalisation, but **inner spacing
matters**: `is  sitting` (two spaces) will not match `is sitting`.

### Mixing mechanics in one exercise

```jsonc
{
  "pools": { "quant": [
    { "id": "q_a", "text": "a" }, { "id": "q_some", "text": "some" }
  ]},
  "slots": [
    { "id": "s1", "label": "I need ___ help with this ticket.",
      "input": "select", "pool": "quant", "answer": ["q_some"] },
    { "id": "s2", "label": "She ___ the bug yesterday.",
      "input": "text", "answer": ["fixed"] }
  ]
}
```

## 6. Rules that silently break things

These do not throw. They produce a broken exercise that looks fine.

### 6.1 `answer` references item **IDs**, never text, never positions
```jsonc
"answer": ["v_sits"]   // ✅ the item's id
"answer": ["sits"]     // ❌ the visible text — will never match
"answer": [1]          // ❌ a position — breaks when options are shuffled
```
The site shuffles options on render. A positional answer means the learner picks
correctly and is marked wrong.

### 6.2 Make pool IDs **different** from their visible text
```jsonc
{ "id": "q_some", "text": "some" }   // ✅
{ "id": "some",   "text": "some" }   // ❌ works, but hides bugs
```
When the id and the text differ, a bug that reports the text instead of the id
becomes visible immediately instead of passing silently.

### 6.3 List **every** correct answer for `text` slots
```jsonc
"answer": ["has", "eats", "is having"]
```
A learner marked wrong for a correct answer is the worst failure this system can
produce. Think about contractions (`doesn't` / `does not`), alternatives
(`has` / `eats`), and regional spellings (`practise` / `practice`) — list them
all.

### 6.4 One `___` per slot
Only the **first** blank in a label receives the input. If a sentence needs two
blanks, make it **two slots**.

### 6.5 `slug` must be unique per `(level, focus)`
Short, English, kebab-case, and descriptive of the exercise — not of the grammar
(the `focus` already says that). `ordering-coffee`, not `past-simple-3`.

### 6.6 Slugs are permanent
`slug`, `focus` and `level` appear in the URL. Once published, teachers share
those links. Renaming breaks them.

### 6.7 The `focus` must be what the exercise actually tests
A row filed under `past-simple` whose blank tests a preposition is worse than no
row at all.

## 7. Output format

One SQL file. Group by level, then focus, with comments.

```sql
-- English exercises — <level(s)>, <focus(es)>
-- Content only. No schema changes.

insert into public.exercises
  (slug, skill, level, focus, topic, payload, published)
values

-- ---------- A1 · present-simple ----------
('daily-routine', 'writing', 'A1', 'present-simple', 'daily-life', '{
  "pools": {},
  "slots": [{
    "id": "s1",
    "label": "I ___ up at seven every day.",
    "input": "text",
    "answer": ["get", "wake"]
  }]
}', true),

('third-person-s', 'reading', 'A1', 'present-simple', NULL, '{
  "pools": { "verbs": [
    { "id": "v_work",  "text": "work"  },
    { "id": "v_works", "text": "works" }
  ]},
  "slots": [{
    "id": "s1",
    "label": "My sister ___ in a hospital.",
    "input": "choice",
    "pool": "verbs",
    "answer": ["v_works"]
  }]
}', true)

on conflict (level, focus, slug) do nothing;

-- Verification
select level, focus, count(*) from public.exercises
group by level, focus order by level, focus;
```

### Format requirements
- **`on conflict (level, focus, slug) do nothing`** at the end — the file must be
  safe to run twice.
- `topic` is either a quoted slug or bare `NULL` (no quotes).
- `published` is `true` for finished exercises.
- The payload is a single-quoted JSON string. **If your English content contains
  an apostrophe** (`don't`, `it's`), you must escape it by doubling it inside the
  SQL string: `"answer": ["doesn''t"]`. This is the single most common way these
  files fail to run.

---

## 8. Checklist before you deliver

Go through every exercise:

- [ ] `level`, `focus`, `topic`, `skill` are copied **exactly** from §3
- [ ] No `listening` rows
- [ ] `slug` is unique within its `(level, focus)`
- [ ] The `focus` is genuinely what the exercise tests
- [ ] Vocabulary and sentence length match the CEFR level
- [ ] Every `answer` id exists in the referenced pool
- [ ] `choice`/`select` pools have **at least 2 items**
- [ ] `text` slots have no pool, and list **every** acceptable answer
- [ ] Every `label` contains `___`, and **only one** per slot
- [ ] Pool ids differ from their visible text
- [ ] Apostrophes inside the JSON are **doubled** (`don''t`)
- [ ] Mechanics vary — not five identical multiple-choice items in a row
- [ ] The JSON parses (check it, do not assume)
- [ ] The file ends with `on conflict … do nothing`

---

## 9. Quality bar

- **The exercise must be answerable from the sentence alone.** If several options
  are grammatically valid in the given context, the exercise is broken — even
  though it will grade "correctly".
- **Vary the mechanics within a focus.** Five identical multiple-choice items is
  a worksheet, not practice.
- **Context is a feature.** "Present simple, in a standup" teaches more than
  "Present simple". But use `topic: NULL` when there genuinely is no context —
  do not fabricate one.
- **The audience is developers, but not every exercise is technical.** Mix
  workplace situations (standups, code review, interviews) with everyday English
  (food, travel, family). Both matter for real acquisition.
- **Write natural English.** These are sentences a person would actually say, not
  grammar-book specimens.
